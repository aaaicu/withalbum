# 성능 측정 (합성 라이브러리 10만·50만 자산)

`scripts/perf-bench.sh`(+ `tools/perf/`)로 측정한 결과입니다. **실제 사진이 아닌 합성 데이터**입니다: 실제 업로드 1건을 API로 보낸 뒤, 그 DB 행(blob·자산·폴더 연결·`asset_added` 이벤트)을 한 트랜잭션에서 N-1번 복사하고 자산마다 24~39바이트짜리 고유 원본 파일을 pool에 만듭니다. 따라서 원본 크기에 비례하는 비용(해시·복사·디스크 대역폭)은 실제보다 훨씬 작고, **파일 개수와 DB 행 수에 비례하는 비용**을 보는 측정입니다.

```bash
bash scripts/perf-bench.sh -n 100000,500000 -r /tmp/perf.md   # 50만은 디스크 약 3GB, 10분 정도
```

## 환경

| 항목 | 값 |
|---|---|
| 기계 | Apple Silicon Mac (arm64, 8 CPU, 메모리 16GB), 내장 SSD(APFS) |
| OS | macOS 27.0.1 |
| 서버 | 이 저장소의 `withalbum-server`(`CGO_ENABLED=0 -trimpath`), Go 1.27.2 |
| 측정일 | 2026-10-20 |
| 데이터 | 폴더 1개에 N개 자산, 원본 N+5개(합성 N개 + 실제 업로드 5개) |

시간은 클라이언트(같은 Mac, 루프백 HTTP)에서 잰 벽시계 시간입니다. 최대 RSS는 해당 프로세스의 `ru_maxrss`(서버는 아래 모든 HTTP 단계를 거친 뒤 종료 시점의 최대값, `verify`는 그 명령 프로세스).

## 결과

| 단계 | 10만 | 50만 | 비고 |
|---|---:|---:|---|
| 합성(서버 아님) | 42.3 s | 4.1 min | DB 119 MiB / 597 MiB |
| 서버 기동 → `/health` 응답 | 1.1 s | **44.8 s** | 기동 재조정이 모든 원본의 크기를 확인(아래 "발견") |
| `GET /folders` | 5 ms | <1 ms | |
| 스냅샷 `GET /folders/{id}/assets` 전체(500개씩) | 2.2 s (200쪽, 11.1 ms/쪽) | 9.6 s (1000쪽, 9.6 ms/쪽) | 키셋 페이징: 쪽당 시간이 크기와 무관 |
| 스냅샷 한 쪽, 90% 깊이 | 9 ms | 9 ms | 20회 평균 |
| 이벤트 `GET /sync` 처음부터 전체(500개씩) | 1.8 s (9.0 ms/쪽) | 9.8 s (9.8 ms/쪽) | |
| 이벤트, 스냅샷 cursor부터(최신) | <1 ms | <1 ms | |
| 64 KiB 업로드(큰 폴더, fsync 포함) | 20 ms (최대 29) | 17 ms (최대 18) | 5회 평균 |
| 서버 최대 RSS | 163 MiB | 165 MiB | 대부분 Argon2id 로그인 해시(64 MiB × 동시 2)·프로세스 기본; 라이브러리 크기와 거의 무관 |
| `verify` (존재·크기) | 5.2 s / 27 MiB | 60.5 s / 30 MiB | |
| `verify -hash` | 20.8 s / 28 MiB | 2.1 min / 28 MiB | 합성 원본은 수십 바이트라 해시 비용은 거의 파일 열기 비용 |

메모리는 라이브러리 크기에 따라 늘지 않습니다(재조정·verify는 정렬 병합/짧은 쪽 단위 질의).

## 발견

- **DB 질의는 병목이 아님.** 스냅샷·이벤트 페이지가 10만·50만에서 같은 시간(약 10 ms/500개, 대부분 JSON 인코딩)이고, 큰 폴더에 대한 업로드 시간도 그대로입니다. 크기에 비례하는 질의(스냅샷 쪽, 이벤트 쪽, 자산의 폴더들, 촬영 시각·프리뷰 대기열, 재조정 blob 목록, 영수증 조회·정리)가 모두 인덱스를 쓰는지 `EXPLAIN QUERY PLAN`으로 확인했고, 회귀를 막는 테스트를 추가했습니다(`internal/meta/sqlitestore/queryplan_test.go`). 빠진 인덱스는 찾지 못해 스키마 변경은 없습니다.
- **기동과 `verify`는 파일 개수에 대해 선형보다 나빠짐.** 10만 → 50만에서 기동 1.1 s → 44.8 s, `verify` 5.2 s → 60.5 s. 원인은 파일 시스템입니다: pool 파일 50만 개에 `lstat`만 하는 단독 프로그램도 데이터가 캐시된 상태에서 33 s(파일당 약 66 µs)가 걸렸고, 이 Mac의 vnode 캐시(`kern.maxvnodes` = 250,343)보다 파일이 많아 매번 메타데이터를 다시 읽습니다. 10만 개는 캐시에 다 들어가 파일당 약 10 µs입니다. 메모리가 더 큰 Mac은 vnode 캐시가 커서 경계가 뒤로 밀립니다.
  - 영향: 50만 장 규모 라이브러리는 서버 시작(재부팅·재시작·디스크 재연결 후)에 내장 SSD에서도 1분 가까이 걸리며, 그동안 `/health`가 응답하지 않습니다(메뉴 막대 앱은 "시작하는 중"). 외장 HDD에서는 훨씬 길 것입니다(미측정).
  - 후속 후보(이번에는 하지 않음): 기동 재조정을 `getattrlistbulk(2)`(macOS)로 디렉터리 단위 일괄 조회, 또는 기동 시에는 이름만 대조하고 크기 확인은 백그라운드로 돌리기. 데이터 안전 판정(누락·크기 불일치 경고)의 시점이 바뀌므로 설계 결정이 필요합니다.

## 측정하지 않은 것

- 실제 사진·영상 크기의 원본(해시·복사·백업 시간), 외장 HDD/SSD(USB·Thunderbolt), Raspberry Pi·Linux.
- 여러 폴더·여러 사용자에 나뉜 라이브러리, 동시 업로드·동시 동기화 부하, 프리뷰·촬영 시각 워커가 대량 백필할 때의 시간.
- `backup`(50만 원본 증분 복사)과 `restore`.
